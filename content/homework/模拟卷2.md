**1.** 总时延由发送时延、传播时延、处理时延和排队时延组成。关于这四种时延，以下说法正确的是？

A. 发送时延发生在传输媒体上，与信道长度有关
B. 传播时延发生在路由器内部，与信号发送速率有关
C. 排队时延取决于网络当时的通信量，队列溢出时相当于时延为无穷大
D. 处理时延就是路由器将分组从输入端口复制到输出端口的时间

<details>
<summary>答案</summary>

**C**

A 错，发送时延发生在**机器内部的发送器**，与信道长度无关。
B 错，传播时延发生在**机器外部的信道**上，与信号发送速率无关。
C 对，队列溢出 → 分组丢失 → 相当于排队时延为无穷大。
D 错，处理时延是分析首部、差错检验、查找路由的时间。

</details>

**5.** 数据链路层使用 PPP 协议在同步传输链路上传送数据。若数据部分出现比特序列 `0111111011111100`，经过零比特填充后实际发送的比特序列是？

A. 0111111011111100
B. 01111101011111000
C. 01111110011111000
D. 01111110101111100

<details>
<summary>答案</summary>

**B**

零比特填充规则：发送端每遇到 **5 个连续的 1**，在其后**插入一个 0**。

逐段处理 `0111111011111100`：
- `011111` → 5个连续的1 → `0111110`
- 接着 `10` → 只有1个1，不填充 → `10`
- 接着 `11111` → 5个连续的1 → `111110`
- 接着 `00` → 不填充 → `00`

完整结果：`0111110` + `10` + `111110` + `00` = **01111101011111000**

</details>

### 1. 虚电路服务与数据报服务（6 分）

网络层可以向上提供虚电路服务和数据报服务两种。请从以下方面对比：
1. 连接的建立
2. 分组的转发路径
3. 结点故障时的表现
4. 分组的到达顺序
5. 互联网采用的是哪一种？为什么？

<details>
<summary>答案</summary>

| 对比方面 | 虚电路服务 | 数据报服务 |
|---------|----------|----------|
| 连接建立 | **必须**先建立连接 | **不需要** |
| 转发路径 | 同一虚电路的分组走**同一路由** | 每个分组**独立选路** |
| 结点故障 | 经过故障结点的虚电路**全部不工作** | 可能丢失分组，路由可能变化 |
| 到达顺序 | **按序**到达 | 不一定按序 |

互联网采用**数据报服务**。原因：
- 设计思路：网络层尽量简单，把复杂性放在端系统
- 路由器只需要转发分组，不需要维护连接状态
- 互联网规模巨大，端到端可靠通信由运输层的 TCP 保证
- 可以适应网络拓扑的动态变化，有更好的健壮性

</details>

### 2. CRC 校验的局限性（6 分）

在数据链路层中，CRC 循环冗余检验被广泛使用。请回答：
1. CRC 校验能检测出哪些类型的错误？
2. CRC 校验通过是否意味着传输绝对无差错？为什么？
3. 数据链路层使用 CRC 校验后，是否就实现了可靠传输？如果不是，还需要什么机制？

<details>
<summary>答案</summary>

**1. 能检测的错误类型：**
- 所有单比特错误
- 所有奇数个比特错误（当除数含 X+1 因子时）
- 所有长度不超过 n 的突发错误（n 为冗余码位数）
- 绝大多数长度超过 n 的突发错误

**2. 不是绝对无差错。** CRC 校验通过只意味着"以非常接近于 1 的概率"认为帧在传输中没有产生差错。可能存在某些错误模式恰好使余数为 0 而 CRC 无法检测（尽管概率极低）。

**3. 没有实现可靠传输。** CRC 只能做到"无差错接受"（accept）——即凡是接受的帧都非常可能是正确的。但：
- 发现错误的帧只是被丢弃，**不会重传**
- 可能出现**帧丢失、帧重复、帧失序**
- 可靠传输还需要：**帧编号、确认机制、超时重传**

</details>

### 3. TCP 的流量控制机制（6 分）

TCP 如何利用滑动窗口实现流量控制？请说明接收窗口（rwnd）、发送窗口、拥塞窗口（cwnd）之间的关系。什么是"糊涂窗口综合症"？如何解决？

<details>
<summary>答案</summary>

**滑动窗口实现流量控制：**
- 接收方在 TCP 报文段首部的**窗口字段**中写入自己的接收窗口 rwnd
- rwnd 告诉发送方：从确认号算起，自己还能接收多少字节的数据
- 发送方的发送窗口不能超过 rwnd
- 当 rwnd = 0 时，发送方停止发送（除零窗口探测报文外）

**三个窗口的关系：**
发送窗口上限 = min(rwnd, cwnd)
- rwnd < cwnd → 发送速率受限于接收方的接收能力（流量控制主导）
- cwnd < rwnd → 发送速率受限于网络的拥塞程度（拥塞控制主导）

**糊涂窗口综合症：**
- **发送方糊涂窗口**：应用进程每次只写入极少字节（如1字节），TCP 立即发送 → 有效数据率极低（1字节数据 / 41字节报文）
  - 解决：**Nagle 算法**——积累到 MSS 或收到之前数据的 ACK 后再发送
- **接收方糊涂窗口**：应用进程每次只读取极少字节，窗口只增大极少 → 发送方只能发送极小数据
  - 解决：接收方等待缓存有足够空间（MSS 或一半缓存）后再发确认并通知窗口

**零窗口与死锁防止：**
- 收到 rwnd=0 → 启动**持续计时器**
- 到期 → 发送**零窗口探测报文段**（1字节数据）
- 对方回复当前窗口值 → 打破死锁

</details>

### 4. 万维网 HTTP 连接方式（6 分）

请说明 HTTP/1.0 和 HTTP/1.1 在连接方式上的主要区别。一个主页 HTML 文件包含 5 张图片，分别计算使用以下三种方式时，从发起请求到收到所有内容所需的最短时间（不考虑文档本身的传输时间，只计算 RTT 开销）：
1. HTTP/1.0 非持续连接
2. HTTP/1.1 持续连接（非流水线方式）
3. HTTP/1.1 持续连接（流水线方式）

<details>
<summary>答案</summary>

**HTTP/1.0 vs HTTP/1.1：**
- HTTP/1.0：**非持续连接**。每次请求/响应都新建一个 TCP 连接，完成后释放。每个 TCP 连接开销 2RTT。
- HTTP/1.1：**持续连接**。一个 TCP 连接可传送多个请求和响应。分非流水线和流水线两种。

**时间计算（6 个文档：1个HTML + 5张图片）：**

**(1) HTTP/1.0 非持续连接：**
每个文档新建 TCP → 2RTT + 文档传输（忽略 = 0）
6 个文档需建立 6 个 TCP 连接 → 6 × 2RTT = **12 RTT**

**(2) HTTP/1.1 持续连接，非流水线：**
只建立 1 个 TCP 连接（2RTT），然后：
发送请求1 → 等待响应1 → 发送请求2 → 等待响应2 → ...
每个后续请求经过 1RTT
总时间 = 2RTT + 6 × 1RTT = **8 RTT**

**(3) HTTP/1.1 持续连接，流水线：**
1 个 TCP 连接（2RTT），连续发送 6 个请求，服务器连续响应
但在流水线中，所有请求发出后，响应陆续返回
实际上：建立连接 1.5RTT？HTTP 标准为 2RTT 建立连接。
请求 6 个文档：发第一个请求 + 等响应 = 1RTT（其他请求并行处理）
总时间 ≈ 2RTT + 1RTT = **3 RTT**

> 标准答案：非流水线方式下每个文档串行请求响应，流水线可并行。
> HTTP/1.0: 12RTT
> HTTP/1.1 非流水线: 2RTT + 6RTT = 8RTT  
> HTTP/1.1 流水线: 2RTT + 1RTT = 3RTT

</details>

要发送的数据为 **110011**。采用的生成多项式为 P(X) = X^4 + X^3 + 1。

### 3. IP 数据报分片与 ICMP（8 分）

一个 IP 数据报总长 **5000 字节**（固定首部 20 字节），**标识 = 8888**，**DF = 0**。需要经过两个网络：

- 网络 1：MTU = 1500 字节
- 网络 2：MTU = 800 字节

1. **(3 分)** 数据报经过网络 1 后被分为几个分片？写出每个分片的：总长度、标识、MF、片偏移。
2. **(3 分)** 网络 1 产生的分片到达网络 2 后，网络 2 的 MTU 更小，是否需要再次分片？如果需要，写出第一个分片（原片偏移=0 的那片）再次分片后的结果。
3. **(2 分)** 若原始数据报的 DF = 1（不允许分片），经过网络 1 时会发生什么？

<details>
<summary>答案</summary>

**(1) 经过网络 1**（MTU=1500）（3 分）：

- 数据部分 = 5000 − 20 = **4980 字节**
- 每片最大数据 = 1500 − 20 = **1480 字节**（8的倍数）
- 4980 = 1480 + 1480 + 1480 + 540 → 4 片

| 分片 | 总长度 | 标识 | MF | 片偏移 |
|:--:|:--:|:--:|:--:|:--:|
| 1 | 1500 | 8888 | 1 | 0 |
| 2 | 1500 | 8888 | 1 | 185 |
| 3 | 1500 | 8888 | 1 | 370 |
| 4 | 560 | 8888 | 0 | 555 |

片偏移：
- 片1: 0/8 = 0
- 片2: 1480/8 = 185
- 片3: 2960/8 = 370
- 片4: 4440/8 = 555

**(2) 经过网络 2**（MTU=800）（3 分）：

**需要再次分片。** 因为网络 1 产生的分片总长 1500 > 网络 2 的 MTU 800。

以**第一个分片**（总长 1500，数据 1480，片偏移 0）为例：
- 此片数据 = 1500−20 = 1480 字节
- 网络 2 每片最大数据 = 800−20 = 780 → 取 8 倍数 = **776 字节**

| 子分片 | 总长度 | 标识 | MF | 片偏移 |
|:--:|:--:|:--:|:--:|:--:|
| 1-1 | 796 | 8888 | 1 | 0 |
| 1-2 | 724 | 8888 | 1 | 97 |

片偏移：
- 1-1: 原偏移 0 + 0/8 = 0？实际上是 0 + 0/8 = 0 ✓
- 1-2: 0 + 776/8 = 97

注意：再次分片时，MF 保持原分片的 MF（=1），片偏移在原分片偏移基础上累加。

**(3) DF = 1**（2 分）：

路由器发现数据报总长（5000）> MTU（1500）且 DF=1（不允许分片）→ **丢弃该数据报**。

路由器向源站发送 **ICMP 差错报告报文**：类型 = 3（终点不可达），代码 = 4（需要分片但 DF 置位）。

### 4. TCP 拥塞控制全过程分析（8 分）

- RTT 1~5：正常传输，无拥塞
- RTT 6：发生**超时**
- RTT 7~9：超时后恢复正常，无拥塞

<details>
<summary>答案</summary>

**(1) 完整表格**（5 分）：

| RTT | cwnd | ssthresh | 当前阶段 |
|:---:|:---:|:---:|------|
| 1 | **1** | 32 | 慢开始 |
| 2 | **2** | 32 | 慢开始 |

| 10 | **8** | **8** | 3个重复ACK → 快恢复 → 拥塞避免 |
| 11 | **9** | 8 | 拥塞避免 |
| 12 | **10** | 8 | 拥塞避免 |
| 13 | **1** | **5** | 超时 → 慢开始 |

详细推导：

- RTT 1~5：慢开始指数增长 1→2→4→8→16→32? 等等，RTT=5 时 cwnd=32，cwnd=ssthresh
  - RTT1: cwnd=1
  - RTT2: cwnd=2 (翻倍)
  - RTT3: cwnd=4 (翻倍)  
  - RTT4: cwnd=8 (翻倍)
  - RTT5: cwnd=16 (翻倍)

- RTT 6：超时。此时 cwnd=16 → ssthresh = max(16/2, 2) = 8, cwnd=1

- RTT 7~9：慢开始。1→2→4→8（RTT9 cwnd=8, ssthresh=8）

- RTT 10：收到 3 个重复 ACK。cwnd=8 → 快恢复：ssthresh=cwnd/2=4, cwnd=ssthresh=4

- RTT 11：拥塞避免，cwnd=5
- RTT 12：拥塞避免，cwnd=6

- RTT 13：超时。cwnd=6 → ssthresh = max(6/2, 2) = 3, cwnd=1

**(2) 统计**（3 分）：

**慢开始**：**3 次**
- 第 1 次：RTT 1~5（连接建立后初始）
- 第 2 次：RTT 6~9（第 1 次超时后）
- 第 3 次：RTT 13~（第 2 次超时后）

**拥塞避免**：**2 次**
- 第 1 次：RTT 10~12（快恢复后进入，cwnd 从 4 线性增长到 5、6）
- 注：RTT=5 时 cwnd=16<ssthresh=32，还没进入拥塞避免

**切换原因：**
- 慢开始 → 拥塞避免（RTT 10）：收到 3 个重复 ACK → 快恢复 → 拥塞避免
- 拥塞避免 → 慢开始（RTT 6 和 RTT 13）：**超时**（判断网络发生拥塞）

</details>

## 参考答案与详细解析

---

### 一、单项选择题

**1. C — 服务器发送随机数，用户用密码运算后返回**

质询-应答协议（Challenge-Response）的核心流程：
1. 服务器生成随机数（质询/Challenge）发送给客户端
2. 客户端用密码 + 随机数进行运算（如HMAC(密码, 随机数)），返回结果
3. 服务器用本地存储的密码做同样运算，对比结果

**安全优势**：密码本身不通过网络传输，且每次认证的质询不同，防御重放攻击。但注意C选项中的"所有类型"绝对化表述是错误的——MITM攻击中，攻击者可以转发质询和响应。

**2. C — 通过隐藏部分列或行，实现细粒度的访问控制**

视图（View）是数据库安全的重要机制：
- 隐藏敏感列：如员工表中不暴露工资列
- 隐藏敏感行：如只显示本部门的员工记录
- 视图本身不加密数据（B错），不替代认证（D错），性能不是主要目的（A错）

**3. A — 所有者可读写执行，同组用户可读执行，其他用户无权限**

UNIX权限位 `rwxr-x---` 的解读：
- 前三位 `rwx`：所有者（Owner）= 读 + 写 + 执行
- 中三位 `r-x`：同组（Group）= 读 + 执行（无写权限）
- 后三位 `---`：其他（Others）= 无任何权限

E选项：`---`不是可读写——注意最后一个位组是`---`，意为无权限。

**4. B — 默认拒绝原则**

默认拒绝（Default Deny）原则：凡未被明确允许的一律拒绝。题目中"仅允许...拒绝所有..."正是此原则的体现。最小权限原则是在允许的基础上限制权限范围，与"默认拒绝"互为补充但不完全相同。

**5. C — NTP反射放大攻击**

反射放大攻击的核心特征：利用协议的不对称性——请求很小，响应远大于请求。
- DNS反射放大：~54B请求 → 3000B+ 响应，放大~54倍
- NTP反射放大（monlist命令）：~234B请求 → 可达数十KB，放大可达数百倍
- SYN Flood：无放大效应（纯粹消耗连接资源）
- HTTP Flood：请求和响应相当
- Ping of Death：发送超大包，非放大

**6. C — 最后一条规则：拒绝 所有**

防火墙规则按顺序匹配。最后一条设置为"拒绝所有"（Deny All）正是"默认拒绝"原则的实现——所有未被前面规则明确放行的流量都被最终这条拒绝。如果在第一条就拒绝所有，则后续规则永远不会被匹配。

**7. B — 缓冲区溢出漏洞**

`gets()`函数从标准输入读取数据到`dest`缓冲区（仅16字节），但**不检查输入长度**。如果用户输入超过15个字符（留一位给`\0`），数据会溢出到栈上相邻内存。`gets()`因无法安全使用，在C11标准中已被移除，应使用`fgets(dest, sizeof(dest), stdin)`替代。

**8. B — APT具有明确的攻击目标，且长期潜伏、持续渗透**

APT ≠ 高级恶意软件。APT的核心特征：
- 有明确的攻击目标（特定组织、行业或国家）
- 长期潜伏（数月甚至数年）
- 持续渗透（不急于一次拿下）
- 不一定要用0day（C对/D错）；"Advanced"指的是攻击者资源和能力而非技术本身（A不完全）

**9. D — 定期备份数据库**

备份是数据恢复手段，对防御SQL注入**无效**（注入发生时无法阻止）。但备份对**降低注入后的损失**有帮助。A（参数化查询）是根本防御，B（输入转义）是辅助防御，C（最小权限）是纵深防御的一部分。

**10. C — 会话恢复通过会话ID和缓存的主密钥跳过完整握手**

会话恢复机制：
1. 首次完整握手后，双方保存会话ID和主密钥
2. 后续连接时客户端发送会话ID
3. 服务器在缓存中查找，若找到则直接使用之前协商的密钥，跳过证书验证和密钥交换（减少1个RTT）

TLS 1.3的0-RTT首次连接仍需握手，它是在**恢复**连接时才能0-RTT。

**11. B — 能力表是从主体视角列出该主体可访问的客体及权限**

三种视角的对比：
| 概念 | 视角 | 示例 |
|------|------|------|
| 能力表（Capability List） | 主体视角 | 张三→{文件A:读, 文件B:读写} |
| 访问控制列表（ACL） | 客体视角 | 文件A→{张三:读, 李四:读写} |
| 访问控制矩阵 | 全局二维表 | 行=主体, 列=客体, 值=权限 |

**12. B — UDP Flood**

题干关键特征：
- 大量UDP包
- 目标端口各不相同
- 服务器逐个检查端口→CPU资源消耗

这就是UDP Flood的典型场景。与SYN Flood的区别：SYN Flood用的是TCP SYN包（消耗连接表）。与DNS反射放大的区别：DNS反射放大的源IP为反射服务器（被伪造为受害者），而非攻击者直接发送。

**13. C — 错误的（加盐后攻击者仍可以进行暴力破解）**

加盐的正确理解：
- 加盐 = 为每个密码附加一个随机值（盐），然后一起散列存储
- 作用：使相同密码产生不同散列值，防御**预计算**的彩虹表攻击
- 盐值公开不影响安全性
- **但加盐不能阻止暴力破解**——攻击者只需对每个密码猜测逐个尝试（只是计算量更大）。使用慢散列函数（如bcrypt、Argon2）才能有效增加暴力破解成本。

**14. C — HIDS可以检测主机层面异常，NIDS无法做到**

| 维度 | NIDS | HIDS |
|------|------|------|
| 部署位置 | 网络关键节点（旁路） | 每台重要主机 |
| 数据源 | 网络流量 | 系统日志、文件完整性、系统调用 |
| 典型检测 | 网络攻击（DDoS、扫描、注入） | 文件篡改、异常进程、提权 |
| 加密流量 | 几乎无法检测 | 可以检测（解密后） |

**15. C — 传输模式保留原IP头，隧道模式封装整个原IP包**

| 维度 | 传输模式 | 隧道模式 |
|------|---------|---------|
| 保护范围 | IP载荷（数据） | 整个原IP包 |
| IP头 | 使用原IP头 | 添加新IP头，原IP头被封装 |
| 适用场景 | 主机到主机 | 网关到网关（VPN） |
| 能否同时AH+ESP | 可以 | 可以 |

B说反了，A也错（传输模式也加密数据，只是范围不同）。

**16. B — 作为可信第三方，存储长期密钥并分发短期的票据**

KDC = AS + TGS，是Kerberos的核心。它保存所有用户和服务的长期密钥（从密码派生），但不直接用于通信；而是颁发临时票据和会话密钥用于实际认证。A错（X.509是PKI的概念），C错（NTP是分离的服务），D显然错。

**17. B — IGMP嗅探欺骗攻击可被用来构建组播DDoS**

IGMP（Internet Group Management Protocol）用于管理IP组播组成员关系。攻击者可以利用IGMP的缺陷：
- 伪造IGMP报告加入组播组，接收不属于自己的组播流量
- 利用组播放大效应发起DDoS（一个组播包被复制到组内所有成员）
- IGMP在IPv4和IPv6（MLD）中都有，工作在**网络层**，本身**没有**强认证机制

**18. B — 误报率高，需要细致调整基线**

异常检测的本质问题：
- 什么是"正常"？——基线建模难
- 系统行为随时间变化——基线需要持续更新
- 用户合法但少见的行为容易被判定为异常
- A错（异常检测恰恰擅长未知攻击），C错（需要大量训练数据），D错（异常检测不需要维护攻击特征库）

**19. B — 票据授权票据（TGT）**

Kerberos三种著名攻击：
- **黄金票据（Golden Ticket）**：伪造TGT，攻击者需要获取KDC的KRBTGT账户的密码散列。一旦成功，可以伪造任意用户的TGT，实现永久域控
- **白银票据（Silver Ticket）**：伪造服务票据，针对特定服务
- **Kerberoasting**：破解服务账户的密码

**20. B — 使用多种、多层安全机制叠加，避免单点失效**

纵深防御（Defense in Depth）核心思想：
- 不依赖单一防线（任何防线都可能被突破）
- 多层防御叠加：网络边界(防火墙) → 网络监控(IDS/IPS) → 主机安全(HIDS/EDR) → 应用安全(WAF) → 数据安全(加密/备份)
- 攻击者需要突破多层防御才能到达核心资产
- A是单点防御思维，C/D太过片面

### 二、填空题

**21.** 明、质询

PAP = Password Authentication Protocol，用户名和密码明文传输，不安全。
CHAP = Challenge Handshake Authentication Protocol，通过质询-应答验证，密码不传输。

**22.** 原像抵抗性（单向性）、抗碰撞性（抗强碰撞性）

密码学散列函数的三个安全要求：
1. **原像抵抗性**（Pre-image Resistance）：给定h，无法找到x使得Hash(x)=h（单向）
2. **第二原像抵抗性**（Second Pre-image Resistance）：给定x，无法找到x'≠x使得Hash(x')=Hash(x)
3. **抗碰撞性**（Collision Resistance）：无法找到任意x≠x'使得Hash(x)=Hash(x')（最强要求）

**23.** 安全、强制

MAC = 强制访问控制（Mandatory Access Control）。系统管理员为主体（如用户、进程）和客体（如文件、目录）分配安全标签（如：绝密、机密、秘密、公开），基于标签由系统强制执行访问控制规则。

**24.** 带宽、资源、资源

拒绝服务攻击的三类目标：
- 网络带宽：发送大量数据包占满带宽（如UDP Flood）
- 系统资源：消耗CPU/内存/连接表（如SYN Flood）
- 应用资源：耗尽应用的请求处理能力（如HTTP Flood/Slowloris）

**25.** 握手协议、记录协议

TLS四个子协议的分工：
- **握手协议**：协商参数 + 密钥交换 + 身份认证
- 密码规范协议：确认加密算法
- 报警协议：传递错误/警告
- **记录协议**：实际数据的分片、加密、传输

**26.** 检测器（Sensor）、分析器（Analyzer）、用户接口（Manager/UI）

IDS三组件的数据流：
```
检测器 → 分析器 → 用户接口
（采集）  （判断）  （展示/告警）
```

### 三、判断题

**27. √** — FAR（False Acceptance Rate，错误接受率）和FRR（False Rejection Rate，错误拒绝率）本质上是反比关系。调整生物识别系统的阈值：降低阈值→FAR升高但FRR降低；提高阈值→FAR降低但FRR升高。系统需要在安全性和便利性之间权衡。

**28. ×** — DAC（自主访问控制）的核心特征是**资源所有者**来决定访问权限，而非系统管理员。系统管理员统一分配是MAC的特征。

**29. √** — 时间盲注（Time-based Blind SQL Injection）通过在SQL中注入`sleep(N)`或`benchmark()`等延时函数，根据页面返回时间判断条件真假。例如：`IF(SUBSTRING(password,1,1)='a', SLEEP(5), 0)`——如果页面延迟5秒，说明首字符为'a'。逐字符推断，效率较低但隐蔽性强。

**30. √** — 此判断正确。托管语言（Java、C#、Python等）运行在虚拟机/解释器上，它们自动进行数组边界检查，超出边界会抛出异常而非覆盖相邻内存。缓冲区溢出**本质上**是因缺乏自动边界检查导致的，而C/C++恰好不提供此机制。

**31. √** — 木马的两大特征：①伪装成合法/有用软件引诱用户下载；②依赖社会工程学传播。与蠕虫的核心区别：木马不自动传播，需要用户"主动"下载安装。

**32. ×** — DMZ（隔离区）用于放置**对外提供服务的服务器**（Web、邮件、DNS），而非内部核心服务器。核心数据库应放在内部安全网络中，受到内部防火墙的严格保护。将数据库放在DMZ中恰恰是严重的安全错误。

**33. √** — Snort是开源NIDS的事实标准，由Martin Roesch创建，现属Cisco。支持实时流量分析、协议分析、内容匹配，可通过规则语法灵活定义检测逻辑。

**34. √** — TLS 1.3（RFC 8446）移除了所有被认为不安全的算法：RC4（流密码，已知偏置）、MD5/SHA-1（散列碰撞）、CBC模式（Padding Oracle攻击）、静态RSA密钥交换（无前向安全性）。同时大幅简化了握手流程。

**35. √** — 过渡技术引入的风险：
- **双栈**：同时运行IPv4和IPv6两套协议栈，攻击面翻倍（需要同时防护两种协议的攻击）
- **隧道**（如6to4、Teredo）：IPv6包封装在IPv4中传输，可能绕过IPv4防火墙规则
- 强制启用IPv6的同时可能忘记配置IPv6安全策略

**36. √** — Need-to-Know = 知情权原则，是最小权限原则在信息访问方面的具体化。即使主体通过了认证并被授权，也只能访问完成其职责所**必须**的信息。例如：HR可以看到员工姓名和部门，但不一定能看到员工的工资。

### 四、简答题

**37. DAC/MAC/RBAC三维对比**

**（1）权限分配的主导方（2分）**：
- **DAC**：资源所有者决定。管理者（如文件属主）自行授予/撤销其他用户的访问权
- **MAC**：系统/安全管理员统一分配。为每个主体和客体分配安全标签，由系统强制执行
- **RBAC**：系统管理员定义角色，将权限绑定到角色上。用户通过被分配角色间接获得权限

**（2）典型应用场景（2分）**：
- **DAC**：个人PC、文件共享、小型协作网络（如Linux/Windows文件系统的rwx权限）
- **MAC**：军事信息系统、政府保密网络、情报系统（如SELinux的强制策略）
- **RBAC**：企业ERP、医院HIS、银行核心系统（如部门经理→审批权限、普通员工→查看权限）

**（3）最易实现职责分离的模型（2分）**：
**RBAC**最适合实现职责分离，原因：
- 通过角色划分自然实现了职责边界：同一用户不能同时拥有"订单创建者"和"订单审批者"两个互斥角色
- 支持静态职责分离（SSD）：用户不能同时被分配两个互斥角色
- 支持动态职责分离（DSD）：用户可以在不同时间扮演不同角色，但不能在同一会话中激活互斥角色
- DAC依赖个体所有者无法全局控制，MAC基于安全标签不直接表达业务职责

**38. ICMP洪泛与Smurf攻击**

**ICMP洪泛攻击**（2分）：攻击者直接向目标发送大量ICMP Echo Request（Ping请求）包，占用目标带宽和处理能力。攻击者自身带宽和攻击流量成正比。

**Smurf攻击**（2分）：
1. 攻击者伪造ICMP Echo Request，源IP设为受害者的IP
2. 将请求发送到目标网络的**广播地址**
3. 子网内所有主机收到广播请求后，**全部**向受害者（被伪造的源IP）回复ICMP Echo Reply
4. 攻击者发送1个包 → 受害者收到N个回应（N=子网内主机数量）

**放大效应原理**（2分）：利用了广播地址的"一对多"特性：攻击者发送1个小请求包 → 网络上几十甚至几百台主机各自回复1个响应包 → 受害者被淹没在海量应答中。放大倍数 = 子网主机数。

防御：在网络边界过滤定向广播包（`no ip directed-broadcast`），入口过滤防止IP伪造。

**39. XSS三种类型的核心区别与HttpOnly Cookie**

**三种类型的核心区别**（4分）：

| 类型 | 脚本位置 | 触发方式 | 危害 |
|------|---------|---------|------|
| **反射型** | URL参数中 | 用户点击恶意链接（<u>非持久</u>） | 单次攻击，需诱导 |
| **存储型** | 存储在服务器数据库 | 用户正常访问页面即触发（<u>持久</u>） | 所有访问者受害 |
| **DOM型** | 纯客户端DOM操作 | 恶意代码在客户端通过修改DOM执行，<u>不经过服务器</u> | 服务器日志中无痕迹 |

**HttpOnly Cookie的作用**（2分）：
- 设置`HttpOnly`标志后，Cookie无法通过JavaScript的`document.cookie`读取
- XSS最常见的攻击目标之一就是窃取Cookie（会话劫持）
- 即使XSS注入成功，恶意脚本也无法读取被HttpOnly保护的Cookie
- **注意**：HttpOnly只防窃取，不能阻止其他XSS攻击（如修改页面内容、键盘记录等）

**40. IPS vs IDS**

**三个维度的区别**（4分）：

| 维度 | IDS | IPS |
|------|-----|-----|
| **部署方式** | 旁路（端口镜像/SPAN），接收流量副本 | 在线串联（inline），所有流量必须流经 |
| **核心功能** | 检测 + 告警 | 检测 + 实时阻断 |
| **业务影响** | IDS故障不影响正常流量 | IPS故障可能完全中断网络（单点故障） |

额外维度（二选一）：
- **性能要求**：IDS只需处理副本，性能压力小；IPS在线处理全部流量，需要极高性能
- **误报后果**：IDS误报→虚假告警；IPS误报→误拦截合法流量，导致业务中断

**IPS在线部署的风险和挑战**（2分）：
- **单点故障风险**：IPS是串联设备，一旦宕机则网络中断。需要部署bypass机制（故障时自动转为直通模式）
- **性能瓶颈**：IPS需要对每个数据包进行深度检查，若性能不足则成为网络瓶颈
- **误拦截风险**：误报率控制要求远高于IDS——误报一次可能造成生产事故
- **加密流量挑战**：HTTPS加密后IPS无法检查内容，需部署SSL解密方案（带来新的性能和隐私问题）

**41. 密码策略分析**

**（1）增强安全性的方面（2分）**：
- **限制密码生命周期**：即使密码被泄露（未被察觉），30天后自动失效，缩短攻击者利用窗口
- **禁止密码复用**：防止用户在多个周期中来回切换相同密码，确保密码真正"新鲜"。如果黑客获取了第N次密码，它无法用于第N+1次登录

**（2）负面效果（2分）**：
- **密码疲劳（Password Fatigue）**：频繁更换密码导致用户选择更弱、更容易记的密码（如递增数字：Password1→Password2→Password3），反而降低安全性
- **写下密码**：记不住频繁更换的密码，用户可能记录在便签上甚至贴在显示器上，引入物理安全隐患
- **"新密码不能与最近5次相同"易被绕过**：用户可能用5个弱密码轮换（Password1→Password2→...→Password5→Password1）
- **增加IT支持成本**：用户频繁忘记密码，增加Helpdesk重置密码的工作量

**（3）改进建议（2分）**：
- **引入密码管理器**：推荐或强制使用密码管理器，用户无需记忆复杂密码，减少密码疲劳
- **延长更换周期 + 提升密码强度**：如90天更换，但要求12位以上含大小写特殊字符，通过长度补偿减少"弱密码循环"
- **有条件更换**：仅在检测到异常登录、密码泄露（对接泄露密码库）时强制更换，而非固定周期。正常使用下不强制更换（这是NIST SP 800-63最新建议）
- **多因素认证兜底**：密码策略的不足用MFA弥补——即使密码较弱，第二因素能提供额外保护

### 五、应用题

**42. IDS告警分析与Snort规则**

**（1）规则字段解释（4分）**：

| 字段 | 含义 |
|------|------|
| `alert tcp` | 告警规则，针对TCP协议 |
| `$EXTERNAL_NET any -> $HOME_NET 80` | 源：外网任意端口 → 目标：内网80端口（Web服务器） |
| `msg:"SQL Injection..."` | 告警信息 |
| `flow:to_server,established` | 方向：流向服务器，且TCP连接已建立 |
| `content:"UNION"; nocase;` | 内容匹配：不区分大小写地匹配"UNION" |
| `content:"SELECT"; nocase; distance:0;` | 紧接着匹配"SELECT"，distance:0表示与前一匹配紧邻（"UNIONSELECT"或"UNION SELECT"） |
| `classtype:web-application-attack` | 分类：Web应用攻击 |
| `sid:1000001` | Snort规则ID（自定义规则从1000001起） |

**（2）是否为真实攻击（3分）**：

**不是**真实的SQL注入攻击。理由：
- URL为 `/search.php?q=apple+union+select+brand+from+products`
- 用户搜索关键词是 `apple union select brand from products`——这是一个描述产品品牌的有效搜索短语
- `+` 在URL中是空格，`q`参数是搜索关键词，整个字符串被当作搜索词提交，不是SQL语句的拼接
- 真实注入中，`UNION SELECT`会出现在恶意构造的闭合引号后，如 `' UNION SELECT ... --`

**（3）签名检测的缺陷（2分）**：

- **误报（False Positive）**：纯模式匹配（字符串匹配）无法区分SQL注入和用户的合法搜索输入。只要HTTP请求中包含"UNION SELECT"即触发，缺乏上下文感知
- **缺乏语义理解**：基于签名的检测只看"形式"不看"语义"，不能判断匹配到的字符串是否确实构成了SQL语句的一部分

**（4）改进规则（3分）**：

```
alert tcp $EXTERNAL_NET any -> $HOME_NET 80 (
    msg:"SQL Injection Attempt - UNION SELECT";
    flow:to_server,established;
    content:"UNION"; nocase;
    content:"SELECT"; nocase; distance:0;
    pcre:"/UNION\s+SELECT\s+/i";   # 增加正则匹配
    content:"'"; distance:0;        # 要求附近有单引号（SQL闭合）
    classtype:web-application-attack;
    sid:1000002;
)
```

改进点：
- 添加`pcre`正则表达式确保UNION和SELECT之间有空格（排除"unionselect"作为普通词的情况）
- 检测附近是否存在单引号`'`（SQL注入常见的引号闭合特征）
- 也可添加`content:"--"`（SQL注释）作为辅助特征，但需注意HTTP请求中`--`可能合法出现

更根本的改进：结合上下文——如果请求参数值被URL编码，且编码内容匹配SQL注入模式，可信度更高。不过这是IDS固有的局限性体现。

**43. 日志异常与安全管理综合分析**

**（1）攻击过程描述（5分）**：

**阶段1：信息收集** — 攻击者确定了管理员用户名（admin）

**阶段2：暴力破解/字典攻击**（03:01 — 03:03）
- 攻击者对`/login.php`发动了约500次POST请求，间隔仅0.2秒
- 使用了自动化工具（Burp Suite、Hydra等）进行口令猜解
- 尝试了一系列常见弱密码：admin123、admin、administrator...
- 在03:03:30，第N+1次尝试成功：`password=P@ssw0rd!`

**阶段3：横向移动**（03:03:30 — 03:03:35）
- 登录成功后立即访问`/admin/dashboard.php`确认权限
- 快速浏览`/admin/users.php`——探查系统中有哪些用户，可能为了创建后门账户或收集目标

**阶段4：数据窃取**（03:04:00）
- 通过`/admin/export_data.php`执行了`SELECT * FROM customers`——窃取全部客户数据
- 这条SQL语句出现在POST参数中，说明该接口可能直接拼接SQL执行（存在SQL注入风险，但此处是攻击者已登录后合法的数据导出功能）

**（2）安全问题（3分）**：

- **① 缺少账户锁定机制**：500次失败登录尝试后仍允许继续尝试。应该配置连续失败N次后锁定账户N分钟
- **② 缺少速率限制**：0.2秒一次的高频率请求未被拦截。应限制单IP单用户的请求频率
- **③ 弱密码允许存在**：管理员密码为`P@ssw0rd!`（属于常见密码变种，出现在字典中）
- **④ 缺少异常行为检测**：凌晨3点（非工作时间）的管理员登录+频繁失败+成功后立即导出大量数据，这一系列异常行为未被任何系统检测到
- **⑤ 缺少IP/地理位置检测**：源IP `192.168.1.100`为内网IP，如果管理员不在内网则可能有VPN或内鬼，但日志未体现二次验证
- **⑥ 敏感操作无审批机制**：导出全部客户数据属于高风险操作，应需要审批或二次验证

**（3）改进方案（4分）**：

**预防（Prevention）**：
- 强制密码复杂度策略 + 对接泄露密码库（HaveIBeenPwned），阻止弱密码和已知泄露密码
- 启用账户锁定策略：连续5次失败锁定15分钟
- 部署速率限制（Rate Limiting）：同一IP每秒最多3次登录请求

**检测（Detection）**：
- 部署IDS分析登录失败的异常模式（高频+大量失败）
- 部署UEBA（用户实体行为分析）：检测偏离正常模式的行为——凌晨登录、登录后立即批量导出数据
- 配置SIEM收集日志，关联分析攻击链，实时生成告警
- 设置告警规则：单用户短时间内大量登录失败 + 成功 → 高优先级告警

**响应（Response）**：
- 制定安全事件响应流程（SOP）：发现暴力破解→临时封锁IP→通知管理员→确认数据是否泄露
- 自动响应：检测到暴力破解时自动将攻击源IP加入黑名单（X分钟内）
- 高危操作审批流：导出敏感数据需要第二人审批；或至少需要二次密码验证

**44. 安全协议综合设计**

**（1）通信协议及前两项需求的满足（4分）**：

采用 **HTTPS（TLS/SSL）** 协议。

- **加密（机密性）**：TLS握手完成后，双方协商出对称会话密钥（如AES-128-GCM），之后所有HTTP数据通过该密钥加密传输，第三方即使截获也无法解密
- **服务器身份验证**：握手过程中服务器发送X.509数字证书。客户端验证：(a)证书由可信CA签发；(b)证书在有效期内；(c)证书中的域名与访问的域名一致；(d)证书未被吊销（OCSP/CRL）。验证通过后，客户端确认正在与真实的银行服务器通信，防止钓鱼

**（2）单点登录（SSO）实现（4分）**：

核心思路：**基于票据的SSO机制**（参考Kerberos思想）。

**方案设计**：
1. 部署统一的**认证中心（Auth Server / CAS Server）**
2. 用户首次登录网银门户时，输入用户名+密码+验证码 → 认证中心验证
3. 认证通过后，颁发**全局会话票据（类比TGT）**，写入用户浏览器的安全Cookie（Secure + HttpOnly）
4. 当用户访问子系统（账户查询、转账、理财）时：
   - 子系统检查Cookie中没有有效"服务票据"
   - 自动重定向到认证中心
   - 认证中心验证全局票据有效 → 无需用户再输入密码 → 直接颁发该子系统的服务票据
   - 用户使用服务票据访问子系统

**另一种方案（更现代）**：
基于OAuth 2.0 + OpenID Connect（OIDC）+ JWT Token：
- 一个授权服务器，多个资源服务器（各子系统）
- 用户登录后获得JWT access token（包含用户身份和scope声明）
- 各子系统验证JWT签名即可获知用户身份
- JWT设置短期有效（如15分钟），配合refresh token实现静默续期

**（3）大额转账的额外验证方案（4分）**：

**方案：行为分析 + 阶梯式二次认证**

**第一层——行为特征分析（无感验证）**：
- 分析用户历史行为基线：常用转账金额范围、常用收款人、常用时间段、常用设备指纹
- 当转账请求偏离基线时触发风险评分，不需打断用户：
  - 轻微偏离（如金额稍高但收款人常用）：仅记录日志
  - 中度偏离（如金额超出日常5倍）：要求输入交易密码
  - 严重偏离（如首次向新收款人转账大额 + 凌晨操作）：强制二次认证

**第二层——二次认证（阶梯式）**：
- "$X万以下（高频场景）"：交易密码 + 短信验证码
- "$X万-$Y万（中风险）"：交易密码 + 人脸识别/指纹
- "$Y万以上（高风险）"：交易密码 + U盾/硬件令牌签名 + 视频客服确认

**安全考量**：
- **信道隔离**：短信验证码不应通过与网银相同的信道发送（如不通过APP推送，而走独立短信通道）
- **交易绑定**：验证码/签名必须绑定本次交易的具体信息（金额+收款人+时间戳），防止MITM攻击中验证码被复用
- **防重放**：每次交易生成唯一交易流水号，签名包含流水号
- **设备绑定**：高风险交易的二次认证应在独立设备上完成（手机/硬件令牌），与发起交易的设备分离

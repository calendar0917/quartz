## 参考答案与详细解析

---

### 一、单项选择题

**1. B — TGS（票据授权服务器）**

| 组件 | 职能 |
|------|------|
| AS | 验证用户身份，颁发TGT |
| **TGS** | 验证TGT，颁发**服务票据** |
| KDC | AS + TGS 的统称 |
| CA | PKI体系，与Kerberos无关 |

**2. C — HMAC结合密钥和散列函数，同时提供完整性和认证**

HMAC = Hash-based Message Authentication Code。它结合共享密钥和散列函数，既验证完整性（防篡改），也提供认证（只有持有密钥的一方才能生成正确的HMAC）。A错（使用对称思想/共享密钥），B错（安全性依赖于密钥的保密性，不单纯依赖抗碰撞性），D错（必须共享密钥）。

**3. D — ABAC**

ABAC可以基于环境属性（如时间）动态决策。"工作时间"属于环境属性，"科室"属于主体属性，"病历"属于客体属性。RBAC无法处理时间约束。DAC/MAC也都不支持这种精细的环境条件。

**4. C — Chinese Wall模型**

Chinese Wall模型的核心就是防止利益冲突——用户访问了某个公司的数据后，就不能再访问其竞争公司的数据。题目中"财务部的只能看财务数据"符合"墙"的概念：访问一侧后自动禁止访问对立侧。BLP/Biba是层级安全模型，Clark-Wilson是职责分离。

**5. C — 读取"秘密"级别的文件**

BLP规则：不能向上读（No Read Up），不能向下写（No Write Down）。"机密"级主体可以读≤机密级（秘密、公开），故C正确。A错（绝密>机密，不可向上读），B错（不能向公开写，会导致机密信息泄露到低级别），D符合规则但不能向上写。

**6. B — XML签名提供三种类型：封装式、被封装式、分离式**

XML数字签名的三种形式：
- 封装式（Enveloping）：签名包含被签名的数据
- 被封装式（Enveloped）：签名包含在XML文档内部
- 分离式（Detached）：签名与被签名数据分开存放

A错（可以对部分元素签名），C错（使用非对称加密），D错（应用不止Web Service）。

**7. C — 联合查询注入（带内注入）**

关键特征：`UNION SELECT` + 攻击结果直接在页面显示。时间盲注无直接回显（通过延时推断），报错注入靠触发数据库报错获取信息，带外注入走DNS等外部信道。

**8. C — 错误的**

NX/DEP的正确含义是标记为**不可执行**（No-eXecute / Data Execution Prevention），而非可执行。将栈/堆标记为不可执行可以防止shellcode运行。C的说法恰好相反，故为错误选项。

**9. D — 自动防御DDoS攻击**

SSH提供三层保护：传输层（加密+服务器认证）、用户认证层（口令/公钥）、连接层（端口转发、X11转发等）。DDoS防御不在SSH功能范围内。

**10. C — 错误的**

状态检测防火墙工作在**网络层到传输层**（维护TCP连接状态），并非应用层。应用代理防火墙才工作在应用层。A、B、D均正确。

**11. B — 假阳性（FP）**

| 真实 | 告警 | 分类 |
|------|------|------|
| 攻击 | 告警 | TP（真阳性） |
| 正常 | 告警 | FP（假阳性/误报） |
| 攻击 | 不告警 | FN（假阴性/漏报） |
| 正常 | 不告警 | TN（真阴性） |

**12. C — 提供邮件的数字签名和数据加密**

S/MIME（Secure/Multipurpose Internet Mail Extensions）在邮件层面提供端到端安全：数字签名（认证+完整性+不可否认）+ 数据加密（机密性）。A/B错（不替代SMTP，不负责路由加密），D非其功能。

**13. B — IPSec在IPv6中是强制性的**

这是IPv6相比IPv4的重要安全改进——IPSec在IPv6协议栈中是强制要求实现的。A错（IPv6不免疫所有攻击），C错（IPv6仍可使用防火墙等安全机制），D错（地址空间大≠不需要防火墙）。

**14. B — 内核态**

修改系统调用表（sys_call_table）需要通过可加载内核模块（LKM）在内核空间操作，属于内核态rootkit的典型行为。用户态rootkit通过替换用户空间程序（如替换/bin/ls）实现，固件级rootkit在BIOS/UEFI层面。

**15. B — HTTPS = HTTP + 数字签名 + 数据加密**

HTTPS通过SSL/TLS实现：数字签名（证书验证身份）→ 非对称加密交换密钥 → 对称加密传输数据。A不完全（443只是端口），C错（必须有证书），D错（身份认证通过非对称加密/数字证书）。

**16. B — 存储型XSS**

关键区分：
- 存储型：恶意脚本**存储在服务器数据库**中，其他用户访问时触发
- 反射型：恶意脚本在URL参数中，需要诱导用户点击
- DOM型：纯客户端，修改DOM环境

题目明确"被存储到数据库并被其他用户浏览时执行"，故为存储型XSS。

**17. C — 保护域**

保护域 = 一个主体在某一时刻拥有的所有访问权限的集合。张三的{读文件A, 读写文件B, 使用打印机}即是他的保护域。访问控制列表（ACL）是客体视角的权限列表。访问控制矩阵是整个系统的二维表。能力表是主体视角的权限列表。

**18. B — ESP可以穿越NAT，AH不能穿越NAT**

| | AH | ESP |
|---|-----|-----|
| 加密 | ✗ | ✓ |
| 认证 | ✓ | ✓ |
| NAT穿越 | ✗（AH覆盖IP头字段） | ✓ |

AH认证覆盖了部分IP头字段（包括源/目的IP），NAT修改这些字段会导致认证失败。ESP的认证不覆盖外层IP头。

**19. B — 错误的**

低交互蜜罐只模拟服务，捕获信息有限；**高交互**蜜罐使用真实完整系统，才能捕获更丰富的攻击细节。B选项说反了。

**20. B — 减少了握手往返次数（RTT），提高了性能**

TLS 1.3相比1.2的核心改进：握手从2-RTT降到1-RTT（首次），0-RTT恢复。同时还移除了不安全算法（RC4、MD5、SHA-1等），默认支持前向安全性。A/C/D均错误。

**23.** 机密（保密）、读、写

BLP = 保护机密性（保密性）。规则：No Read Up（不能向上读），No Write Down（不能向下写）。
Biba相反：保护完整性，No Read Down，No Write Up。

**24.** 参数化（Prepared Statement）、小、大（或体积小、体积大）

DNS反射放大攻击：攻击者发小的DNS ANY查询（~54B），DNS服务器返回大包（~3000B+），放大倍数50+。

**25.** 检测器（Sensor）、分析器（Analyzer）、用户接口/管理器（User Interface/Manager）

### 三、判断题

**26. √** — CA私钥一旦泄露，攻击者可签发任意伪造证书，整个由该CA背书的信任链全部失效。

**27. ×** — RBAC中权限分配给**角色**，用户通过扮演角色间接获得权限，而非直接分配给用户。

**28. √** — 虚拟机逃逸（VM Escape）是指攻击者从虚拟机内部利用Hypervisor漏洞，突破隔离边界，获得宿主机或其他VM的控制权。

**29. ×** — Biba规则：不能向下读（No Read Down）。高完整性主体读低完整性数据会被"污染"，因此不可读。

**30. √** — 带外注入（Out-of-band）的攻击结果不通过Web页面的正常响应返回，而是通过其他信道（DNS、HTTP请求等）传回攻击者处。

**31. ×** — 堆上没有直接的返回地址。堆溢出的攻击路径是覆盖函数指针、虚函数表指针、或内存管理数据结构。

**32. ×** — IDS的特征是**旁路部署**（端口镜像），只监听不阻断。串接部署（inline）是IPS的特征。

**33. √** — "永恒之蓝"（EternalBlue）利用的是Windows SMBv1协议中的缓冲区溢出漏洞（CVE-2017-0144），WannaCry利用它进行蠕虫式传播。

**34. ×** — X.509证书中包含持有者的**公钥**和身份信息，私钥由持有者自行保管，绝不包含在证书中。

**35. √** — 屏蔽子网结构 = 外部防火墙 → DMZ区 → 内部防火墙 → 内部网络。DMZ位于两个防火墙之间。

### 四、简答题

**36. RBAC/ABAC对比**

**（1）RBAC核心授权模型（2分）**：权限分配给角色，用户通过被分配角色获得相应权限。用户不直接拥有权限，而是通过"用户→角色→权限"的间接关系授权。支持角色继承和职责分离。

**（2）ABAC优势（2分）**：
- 更灵活：支持基于多种属性（主体、资源、环境）的动态决策
- 支持上下文感知：考虑时间、位置、设备状态等环境因素
- 策略表达能力更强：可以表达RBAC无法表达的复杂规则（如"仅在工作时间从公司内网访问"）
- 适合云和分布式环境

**（3）三类属性（2分）**：
- **主体属性**：用户特征（角色、部门、安全级别），如"部门=财务部"
- **客体属性**：资源特征（类型、敏感度、所有者），如"文档分级=机密"
- **环境属性**：上下文信息（时间、位置、设备），如"当前时间=工作时间"

**37. TLS握手协议核心流程**

**5步核心流程**（3分）：
1. **ClientHello**：客户端发送支持的TLS版本、加密套件列表、随机数
2. **ServerHello**：服务器选定加密套件，返回服务器随机数
3. **Certificate**：服务器发送自己的数字证书
4. **ClientKeyExchange**：客户端生成预主密钥，用服务器公钥加密发送
5. **Finished**：双方用协商密钥加密Finished消息，验证握手完整性

**预主密钥的作用和安全意义**（3分）：
- **生成所有后续密钥的基础**：客户端随机生成预主密钥，结合双方随机数通过PRF（伪随机函数）生成主密钥，再派生出会话加密密钥和MAC密钥
- **安全性**：预主密钥用服务器公钥加密传输，只有持有私钥的服务器能解密，确保密钥交换的机密性
- **前向安全性**（TLS 1.3）：若使用DHE/ECDHE密钥交换，预主密钥为临时生成，即使服务器私钥未来被泄露，历史会话也无法解密

**38. 数据库推理攻击**

**原理**（2分）：攻击者无法直接查询敏感数据（受访问控制保护），但可以通过组合多次合法查询的结果，推断出本应保密的个体信息。本质是利用统计查询的聚合信息反推个体。

**攻击过程示例**（2分）：
```
步骤1：SELECT COUNT(*), AVG(salary) FROM employees WHERE dept='研发'
      → 返回：COUNT=10, AVG=15000（研发部10人，平均工资15000）

步骤2：SELECT COUNT(*), AVG(salary) FROM employees 
       WHERE dept='研发' AND name!='张三'
      → 返回：COUNT=9, AVG=14000（排除张三后，9人平均14000）

推断：张三的工资 = 10 × 15000 - 9 × 14000 = 24000
```

**防御方法**（2分，至少写一种）：
- **查询结果抑制**：当查询结果集过小（如COUNT < 阈值k）时拒绝返回，或返回"结果集太小"提示
- **数据扰动**：给聚合结果添加随机噪声（差分隐私方法），使得个体数据无法精确反推
- **查询审计**：记录并分析用户的查询历史，检测多次查询的组合是否可能推断出敏感信息

**39. 签名检测 vs 异常检测**

| 维度 | 签名检测（Signature-based） | 异常检测（Anomaly-based） |
|------|---------------------------|-------------------------|
| **原理**（2分） | 将流量/行为与已知攻击特征库精确匹配，类似杀毒软件的病毒库 | 建立正常行为基线（baseline），检测偏离基线的异常行为 |
| **可检测的攻击**（2分） | 只能检测**已知**攻击（特征库中有签名的）。对0day、变种攻击无能为力 | 可以检测**未知**攻击（只要偏离正常模式）。理论上可以检测0day |
| **误报率/漏报率**（2分） | **误报率低**（规则精确），但**漏报率高**（无法检测未知攻击） | **误报率高**（正常变化也可能被视为异常），但**漏报率低**（潜在能发现各种攻击） |

**补充**：现代IDS通常结合两者——签名检测处理已知攻击（快速、准确），异常检测辅助发现新型威胁。

**40. Rootkit分析**

**（1）Rootkit（2分）** — 在干净系统下能看到文件/进程，但在受感染系统中看不到，说明这些对象被rootkit隐藏了。

**（2）工作原理（4分）**：

**用户态rootkit**（2分）：
- 替换系统工具程序（如将`/bin/ls`、`/bin/ps`替换为篡改版本）
- 篡改后的程序在显示时跳过攻击者的文件/进程
- 特点：实现相对简单，但容易被完整性检查工具（如Tripwire）发现

**内核态rootkit**（2分）：
- 通过可加载内核模块（LKM）直接修改操作系统内核
- 劫持系统调用表（sys_call_table）：拦截`getdents`（目录读取）、`read`（文件读取）等系统调用
- 当用户程序调用这些系统调用时，rootkit过滤掉攻击者相关的返回结果
- 特点：极其隐蔽，用户态工具无法检测；比用户态rootkit危害更大；需要内核级防护（如签名验证的内核模块）

### 五、应用题

**41. 防火墙部署设计题**

**（1）拓扑结构（屏蔽子网结构，5分）**：

```
                        Internet
                           │
                    ┌──────┴──────┐
                    │  外部路由器   │
                    └──────┬──────┘
                           │
                    ┌──────┴──────┐
                    │  外部防火墙   │ ← 第一道防线
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
         ┌────┴────┐  ┌───┴───┐  ┌────┴────┐
         │Web服务器 │  │邮件服务器│  │DNS服务器 │ ← DMZ区
         └────┬────┘  └───┬───┘  └────┬────┘
              │            │            │
              └────────────┼────────────┘
                           │
                    ┌──────┴──────┐
                    │  内部防火墙   │ ← 第二道防线
                    └──────┬──────┘
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
    ┌────┴────┐      ┌────┴────┐      ┌────┴────┐
    │员工办公网│      │数据库集群│      │财务系统 │ ← 内部网络
    └─────────┘      └─────────┘      └─────────┘
```

**（2）访问控制策略要点（4分）**：

**外部防火墙规则**：
- ① 允许 Internet → DMZ Web服务器：HTTPS (TCP/443)
- ② 允许 Internet → DMZ 邮件服务器：SMTP (TCP/25)、POP3 (TCP/110)
- ③ 拒绝所有其他来源为Internet的入站流量（默认拒绝原则）

**内部防火墙规则**：
- ④ 允许 DMZ Web服务器 → 内部数据库集群：MySQL (TCP/3306)，仅限已建立连接
- ⑤ 允许 内部员工办公网 → DMZ 邮件服务器：POP3 (TCP/110)、SMTP (TCP/25)
- ⑥ 拒绝 DMZ → 内部财务系统：全部（财务系统仅限内部访问）

**（3）比屏蔽主机结构更安全的原因（3分）**：

- **双重防护**：屏蔽子网使用两道防火墙，攻击者即使突破外部防火墙到达DMZ，仍需突破内部防火墙才能触及核心数据。屏蔽主机只有一道防线
- **DMZ隔离**：对外服务集中在DMZ中，与内部网络物理/逻辑隔离。即使Web服务器被完全攻陷，攻击者仍无法直接访问数据库和财务系统
- **最小暴露面**：屏蔽主机中堡垒主机直连内部网络，一旦被攻破则内部网络全面暴露。而屏蔽子网中DMZ被两道防火墙夹在中间，既限制外部访问，也严格管控向内部的连接

**42. 多因素认证与Kerberos综合分析**

**（1）认证协议及票据作用（4分）**：

该大学使用了**Kerberos**认证协议（基于票据的单点登录）。

| 票据 | 作用 | 颁发者 |
|------|------|--------|
| **TGT**（票据授权票据） | 证明用户已通过初始认证。用户凭TGT可以向TGS请求任意服务的服务票据，无需反复输入密码 | AS（认证服务器） |
| **服务票据** | 证明用户有权访问特定服务。用户持服务票据直接访问目标服务，服务端验证票据即可 | TGS（票据授权服务器） |

核心思想：初始认证一次，后续凭票据访问，实现单点登录（SSO）。

**（2）时钟偏差问题（3分）**：

**原因**：Kerberos在票据中嵌入了**时间戳**用于防止重放攻击。服务器收到票据后，检查票据中的时间戳与当前时间的偏差是否在允许范围内（通常5分钟）。

**为什么对时间同步要求严格**：
- Kerberos依赖时间戳判断票据是否有效（是否过期、是否被重放）
- 如果客户端时钟与KDC时钟偏差过大，合法票据也会被拒绝，导致认证失败
- 这是Kerberos公认的局限性之一，通常通过NTP时间同步服务解决

**（3）引入第二因素（5分）**：

**最佳引入时机**：在**步骤1——客户端向AS请求初始认证时**，引入短信验证码。

**实现方式**：
- 用户输入学号+密码后，AS暂不返回TGT
- AS通过短信网关向用户注册手机号发送一次性验证码
- 用户在客户端输入验证码
- AS验证（密码正确 + 验证码正确）后，才颁发TGT

**理由**：
- 初始认证是最关键的安全关口，一旦TGT被非法获取（如密码泄露），攻击者可以使用TGT持续请求各种服务票据
- 在TGT颁发环节强制双因素认证，确保即使密码泄露也无法获得TGT
- 验证码不通过邮件发送（避免退化为单因素），直接发送到独立于密码信道的手机
- 后续服务票据请求仅依赖TGT，无需再次输入验证码，不影响用户体验

**43. 缓冲区溢出综合分析**

**（1）漏洞类型和位置（3分）**：

**漏洞类型**：栈溢出（Stack Overflow / Stack Buffer Overflow）

**漏洞所在行**：第①行 `strcpy(buffer, input);`

- `buffer`仅声明为32字节，但`strcpy`无条件复制`input`的全部内容
- `input`长度未经任何检查，可能远大于32字节
- 溢出数据会覆盖栈上相邻的内存区域

**（2）绕过认证的攻击原理（5分）**：

**内存布局分析**（以典型x86栈布局为例）：

```
栈增长方向 ↓

高地址
┌──────────────┐
│ 返回地址      │  ← 函数返回时的跳转地址
├──────────────┤
│ 旧的EBP      │
├──────────────┤
│ authenticated │  ← int型变量，4字节，初始值=0
├──────────────┤
│ buffer[31]   │
│    ...       │  ← char buffer[32]
│ buffer[0]    │
└──────────────┘
低地址
```

`authenticated`变量紧邻`buffer`上方（或下方，取决于编译器）。

**攻击手法**：攻击者不需要知道正确密码，只需输入超过32字节的字符串：
- 前32字节填满`buffer`
- 后续字节覆盖`authenticated`变量，将其值从0改为**任何非零值**
- 由于`strcpy`不检查长度，`authenticated`被覆盖为任意非零值
- 函数返回时，`if (authenticated)`判定为真，认证被绕过

**具体实例**：
```bash
# 输入33个字符（32个填充+1个\0以外的任意字符即可将authenticated改为非零）
./program AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA\x01
# 输出：Access Granted! （认证被绕过！）
```

> 如果攻击者继续延长输入，还能覆盖返回地址实现任意代码执行（更严重的后果）。

**（3）三种防御技术（4分）**：

| 防御技术 | 工作原理 |
|---------|---------|
| **Stack Canary（栈保护）** | 编译时在`buffer`和`authenticated`（以及返回地址）之间插入一个随机"金丝雀值"。函数返回前检查该值是否被篡改。由于溢出是连续覆盖，覆盖`authenticated`必然会先破坏金丝雀值，从而被检测到，程序终止而非继续执行。GCC选项：`-fstack-protector` |
| **NX/DEP（不可执行栈）** | 利用硬件NX位（或Windows DEP），将栈内存标记为不可执行。即使攻击者将shellcode写入栈，CPU也会拒绝在栈上执行指令。但本题不需执行shellcode（只需覆盖变量），所以此防御对此特定攻击方法效果有限 |
| **安全函数替换** | 将`strcpy`替换为`strncpy(buffer, input, sizeof(buffer)-1)`，强制限制复制长度不超过缓冲区大小。`strncpy`会在超出限制时截断，防止溢出。类似的安全替代还包括`strlcpy`、`snprintf`等。这是**根本性修复** |
| **ASLR（地址空间随机化）** | 每次运行时随机化栈、堆、库的基地址。对于需要精确覆盖返回地址的高级溢出攻击有效，但对本题简单的变量覆盖（不依赖绝对地址）效果有限 |

**最有效的组合**：安全函数（根本修复） + Stack Canary（运行时兜底） + ASLR + NX（纵深防御）。

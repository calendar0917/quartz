# 第2章 同步互斥与死锁 —— 多个进程怎么合作而不打架

---

## 4.0 从一个故事说起

你和室友共用一台打印机。你刚开始打印论文，室友也发了个打印任务。如果没有任何协调，你的论文第3页可能突然插进室友的一张PPT。

这就是**互斥**问题：打印机在同一时刻只能被一个人用。

再想另一个场景：食堂做饭的师傅（生产者）和打饭的你（消费者）——师傅没做好饭你不能打饭，你没吃完师傅也别做太多。

这就是**同步**问题：两个活动有先后依赖关系。

## 4.1 核心概念——在往下之前务必理解

### 临界资源和临界区

- **临界资源**：一次只能一个进程用的资源（打印机、共享变量）
- **临界区**：程序中**访问临界资源的那段代码**

```c
// 进入区——检查能否进入
P(mutex);
// ▼ 临界区 ▼
共享变量操作;
// ▲ 临界区 ▲
V(mutex);
// 退出区——释放资源
```

### 四条准则（设计同步机制的检验标准）

| 准则 | 含义 | 违反后果 |
|------|------|----------|
| **空闲让进** | 没人在临界区时应允许进入 | 无意义的等待 |
| **忙则等待** | 有人在临界区时必须等 | 数据不一致 |
| **有限等待** | 不能无限期等待 | 饥饿或死锁 |
| **让权等待** | 等不到时应释放CPU | 忙等浪费CPU |

## 4.2 信号量——PV操作的原理

### 为什么软件/硬件方法不够好？

| 方法 | 问题 |
|------|------|
| 软件方法（Peterson等） | 复杂、容易写错、只适用2进程 |
| 硬件TSL/Swap | 忙等（违反让权等待） |
| 中断屏蔽 | 仅单处理器、仅内核可用 |

→ 需要一种高级同步原语：**信号量(Semaphore)**

### 记录型信号量（考试核心）

```c
typedef struct {
    int value;       // 资源计数
    Queue L;         // 等待队列
} Semaphore;
```

#### P操作（wait / 荷兰语Proberen=测试）

```c
P(S) {
    S.value--;           // 先减1，表示"我要一个资源"
    if (S.value < 0)     // 减完发现没了
        block(S.L);      // 把自己挂到等待队列，让出CPU
}
```

#### V操作（signal / 荷兰语Verhogen=增加）

```c
V(S) {
    S.value++;           // 释放一个资源
    if (S.value <= 0)    // 还有人在等
        wakeup(S.L);     // 叫醒一个等待者
}
```

### 信号量值的含义——这是理解PV操作的关键

| S.value | 含义 |
|---------|------|
| > 0 | 还有S.value个空闲资源 |
| = 0 | 资源刚好全部分配完 |
| < 0 | |S.value|个进程在排队等待 |

### 信号量的两种用途

| 用途 | 信号量初值 | P/V位置 |
|------|-----------|---------|
| **互斥** | 1 | 同一个进程中先P后V包围临界区 |
| **同步** | 0（或资源数量） | P在一个进程中，V在另一个进程中 |

## 4.3 用PV操作解题——建模三步法

这是PV操作题的核心方法论。**不是靠背模板，是靠分析关系。**

### Step 1：找出所有的同步和互斥关系

问自己：
- 谁和谁**不能同时做**某事？ → 互斥
- 谁**必须等**谁做完才能做？ → 同步

### Step 2：为每个关系定义一个信号量

- 每个互斥关系 → 一个mutex信号量，初值=1
- 每个同步关系 → 一个信号量，初值=可用资源数（或0表示"还没准备好"）

### Step 3：在正确的位置放P和V

- 互斥：P(mutex) 和 V(mutex) 在**同一个进程**中包围临界区
- 同步：V(S) 在"产生信号的进程"中，P(S) 在"等待信号的进程"中

**黄金法则**：多个P操作时，**先P资源信号量，后P互斥信号量**。顺序颠倒可能死锁！

## 4.4 经典问题——逐个击破

### 问题一：生产者-消费者

**场景**：N个缓冲区，生产者往里放，消费者从里取。

**分析**：
- 互斥关系：缓冲区一次只能一个人操作 → mutex=1
- 同步关系1：缓冲区满了生产者要等 → empty=N（还有N个空位）
- 同步关系2：缓冲区空了消费者要等 → full=0（初始0个产品）

```c
Semaphore mutex = 1, empty = N, full = 0;

Producer() {
    while(1) {
        生产一个产品;
        P(empty);    // ① 申请一个空缓冲区（没空位就等）
        P(mutex);    // ② 锁缓冲区
        放入缓冲区;
        V(mutex);    // ③ 解锁
        V(full);     // ④ 通知消费者：多了一个产品
    }
}

Consumer() {
    while(1) {
        P(full);     // ① 申请一个满缓冲区（没产品就等）
        P(mutex);    // ② 锁
        取出产品;
        V(mutex);    // ③ 解锁
        V(empty);    // ④ 通知生产者：多了一个空位
        消费产品;
    }
}
```

**为什么P(empty)必须在P(mutex)之前？**

假设反过来：
```
Producer: P(mutex) → P(empty)   // 如果empty=0，生产者阻塞在这里
Consumer: P(full)  → P(mutex)   // mutex已被生产者占着，消费者也阻塞
```
→ 生产者等消费者取走产品，消费者等生产者释放锁 → **死锁！**

### 问题二：读者-写者

**场景**：文件可以多人同时读，但读和写、写和写都互斥。

**分析**：
- 写者之间互斥、读写之间互斥 → Wmutex=1
- 多个读者可以同时读 → 用一个计数器Readcount跟踪读者数量
- Readcount本身是共享变量 → 需要rmutex=1保护

```c
Semaphore Wmutex = 1, rmutex = 1;
int Readcount = 0;

Writer() {
    P(Wmutex);   // 整个写操作都在锁内
    写操作;
    V(Wmutex);
}

Reader() {
    P(rmutex);           // 保护Readcount
    Readcount++;
    if (Readcount == 1)  // 第一个读者——要锁住写者
        P(Wmutex);
    V(rmutex);

    读操作;              // 多个读者可以同时读

    P(rmutex);
    Readcount--;
    if (Readcount == 0)  // 最后一个读者走了——放开写者
        V(Wmutex);
    V(rmutex);
}
```

**深入理解**：第一个读者进来时"替大家锁门"（P(Wmutex)），最后一个读者出去时"替大家开门"（V(Wmutex)）。中间的读者进出只需要修改计数器。

**问题**：这个方案是**读者优先**的——只要一直有读者来，写者就可能饿死。

### 问题三：哲学家进餐

**场景**：5个哲学家围坐，5根筷子，需要同时拿左右两根才能吃。

**天真方案**：每人先拿左边再拿右边 → 5人同时拿左 → 死锁！

**三种解法**（理解思路比背代码重要）：

| 方法 | 核心思想 | 破坏了哪个死锁条件 |
|------|----------|-------------------|
| 至多4人同时吃 | 限制并发度 | 环路等待 |
| 左右都可用才拿（AND信号量） | 一次申请所有资源 | 请求并保持 |
| 奇数先左后右，偶数先右后左 | 破坏顺序 | 环路等待 |

写完PV操作后，用这四条检验：

1. **互斥的P和V是否成对**出现在同一进程中？
2. **同步的P和V是否分别**在不同进程中？
3. **多个P操作的顺序**是否正确（资源信号量先于互斥信号量）？
4. 信号量初值是否正确？

## 4.5 死锁

### 死锁的本质

多个进程**互相等待对方持有的资源**，形成环路，谁也不会释放→永远等待。

### 四个必要条件——缺一不可

| 条件 | 含义 | 生活类比 |
|------|------|----------|
| **互斥** | 资源不能共享 | 一把钥匙只开一把锁 |
| **请求并保持** | 占着不放还想要更多 | 左手抓着筷子，右手还要另一根 |
| **不可剥夺** | 别人不能抢你手里的 | 谁也不肯先放下 |
| **环路等待** | 形成等待环 | A等B，B等C，C等A |

### 四种处理方式

#### 方式一：预防（破坏必要条件）

- 破坏"请求并保持"→ 一次性申请所有资源。代价：资源利用率低。
- 破坏"不可剥夺"→ 得不到就释放已有的。代价：可能重复申请。
- 破坏"环路等待"→ 按编号顺序申请。代价：灵活性差。

#### 方式二：避免（银行家算法）

**核心思想**：在分配前先"假装"分配，检查是否安全。安全才真分配。

**安全状态**：存在一个顺序，能让所有进程都完成。

##### 银行家算法完整推导

**数据结构**（用银行贷款类比）：
- Available[m]：银行现金（各类资源可用数）
- Max[n][m]：每个客户的贷款上限
- Allocation[n][m]：已经贷出去多少
- Need[n][m] = Max - Allocation：还需要多少

**步骤**：
1. 客户请求Request[i]
2. 检查：Request ≤ Need？（不超过最大需求）
3. 检查：Request ≤ Available？（银行有这么多现金）
4. 试探分配：Available -= Request, Allocation += Request, Need -= Request
5. 执行**安全性算法**：能找到安全序列→分配；否则→回滚，让客户等

**安全性算法**：
```
Work = Available
Finish[i] = false, 对所有i

循环：
  找一个 Finish[i]==false 且 Need[i] <= Work 的进程i
  如果找到：Work += Allocation[i], Finish[i] = true
  如果找不到：退出循环

如果所有Finish[i]==true → 安全，找到的顺序就是安全序列
否则 → 不安全
```

##### 银行家算法例题

5进程{P0-P4}，3类资源{A,B,C}，总量(10,5,7)

| 进程 | Max | Allocation | Need | 
|------|-----|------------|------|
| P0 | 7,5,3 | 0,1,0 | 7,4,3 |
| P1 | 3,2,2 | 2,0,0 | 1,2,2 |
| P2 | 9,0,2 | 3,0,2 | 6,0,0 |
| P3 | 2,2,2 | 2,1,1 | 0,1,1 |
| P4 | 4,3,3 | 0,0,2 | 4,3,1 |

Available = (10,5,7) - (0+2+3+2+0, 1+0+0+1+0, 0+0+2+1+2) = (3,3,2)

**安全性检查**：Work=(3,3,2)

| 轮次 | 选谁 | 为什么 | Work变化 |
|------|------|--------|----------|
| 1 | P1 | Need(1,2,2) ≤ Work(3,3,2) ✓ | Work += (2,0,0) → (5,3,2) |
| 2 | P3 | Need(0,1,1) ≤ Work(5,3,2) ✓ | Work += (2,1,1) → (7,4,3) |
| 3 | P4 | Need(4,3,1) ≤ Work(7,4,3) ✓ | Work += (0,0,2) → (7,4,5) |
| 4 | P2 | Need(6,0,0) ≤ Work(7,4,5) ✓ | Work += (3,0,2) → (10,4,7) |
| 5 | P0 | Need(7,4,3) ≤ Work(10,4,7) ✓ | Work += (0,1,0) → (10,5,7) |

安全序列：**P1→P3→P4→P2→P0** ✓

**如果P1请求(1,0,2)？**
- Request(1,0,2) ≤ Need(1,2,2)? ✓
- Request(1,0,2) ≤ Available(3,3,2)? ✓
- 试探：Available=(2,3,0), Allocation_1=(3,0,2), Need_1=(0,2,0)
- 重新做安全性检查...（仍然安全）→ 允许分配

#### 方式三：检测与解除

- 用资源分配图判断是否有环路（不可完全简化=死锁）
- 解除：撤销进程或剥夺资源

## 4.6 管程（了解）

管程是比信号量更高级的同步机制：

- 封装了共享变量和操作
- 任何时刻只有一个进程在管程中执行
- 提供条件变量 cwait/csignal

**和信号量的区别**：管程自动保证互斥（不用手动P/V），更不容易出错。

## 1. 运输层概述

### 1.1 运输层的作用

- 为**进程之间**的通信提供服务
- 向高层用户**屏蔽**网络核心细节
- 使应用进程看到端到端的逻辑通信信道

### 1.2 两个主要协议

| | UDP | TCP |
|--|-----|-----|
| 连接 | 无连接 | 面向连接 |
| 可靠性 | 尽最大努力 | 可靠交付 |
| 传输单位 | 用户数据报 | 报文段 (segment) |
| 拥塞控制 | 无 | 有 |
| 适用场景 | 多媒体通信、DNS、RIP | 文件传输、Web、邮件 |

### 1.3 端口号

**端口**：运输层的服务访问点，16 位，范围 0~65535。

| 类型 | 范围 | 说明 |
|------|------|------|
| 熟知端口 | 0~1023 | IANA 分配，全球通用 |
| 登记端口 | 1024~49151 | 在 IANA 登记 |
| 短暂端口 | 49152~65535 | 客户端使用，通信结束收回 |

**重要熟知端口：**

| 端口 | 协议 | 传输层 |
|:---:|------|:---:|
| 21 | FTP 控制连接 | TCP |

| 23 | Telnet | TCP |
| 25 | SMTP | TCP |

| 110 | POP3 | TCP |
| 143 | IMAP | TCP |

| 443 | HTTPS | TCP |
| 520 | RIP | UDP |

## 2. UDP 用户数据报协议

### 2.1 UDP 主要特点

1. **无连接**：发送前不需要建立连接
2. **尽最大努力交付**：不保证可靠
3. **面向报文**：一次交付一个完整报文，**不合并、不拆分**
4. **无拥塞控制**：网络拥塞不降低发送速率（适合多媒体）
5. 支持一对一、一对多、多对一、多对多
6. 首部开销小：仅 **8 字节**

### 2.2 UDP 首部格式

```
 0        15 16       31
┌──────────┬──────────┐
│  源端口    │  目的端口  │
├──────────┼──────────┤
│   长度    │  检验和   │
├──────────┴──────────┤
│       数  据        │
└─────────────────────┘

长度 = 首部(8B) + 数据部分，最小值为 8
```

### 2.3 UDP 检验和

计算时需加 **12 字节伪首部**（仅用于计算）：

```
伪首部格式（12 字节）：
  源 IP 地址 (4B)
  目的 IP 地址 (4B)
  全 0 (1B)
  协议号 17 (1B)
  UDP 长度 (2B)
```

- 检验和 = 对伪首部 + UDP 首部 + 数据按 16 位反码求和，结果取反
- 如果收到报文目的端口号不存在 → 丢弃 + ICMP 发送"端口不可达"

## 3. TCP 传输控制协议

### 3.1 TCP 最主要特点

1. **面向连接**的运输层协议
2. 每条连接只有**两个端点**（一对一/点对点）
3. 提供**可靠交付**
4. **全双工**通信
5. **面向字节流**

**面向字节流**：TCP 不关心应用进程一次发送多长的报文，只把数据看作一连串无结构的字节流。根据对方窗口值和拥塞程度决定报文段包含多少字节。

### 3.2 TCP 连接

- TCP 连接端点 = **套接字 (socket) = (IP地址 : 端口号)**
- TCP 连接 = { socket1, socket2 }
- 同一 IP 地址可有多个不同 TCP 连接
- 同一端口号可出现在多个不同 TCP 连接中

## 4. TCP 报文段首部格式 ⭐⭐

### 固定首部 20 字节

```
 0         4    10   16                31
┌──────┬──────┬────┬───────────────────┐
│ 源端口              │     目的端口      │
├─────────────────────┼───────────────────┤
│                   序号 (seq)            │
├────────────────────────────────────────┤
│                  确认号 (ack)           │
├──────┬──────────┬──┬──┬──┬──┬──┬──┬──┬──┤
│数据偏移│ 保留     │UR│AC│PS│RS│SY│FI│ 窗口 │
│      │         │G │K │H │T │N │N │      │
├──────┴──────────┴──┴──┴──┴──┴──┴──┴──────┤
│         检验和         │    紧急指针      │
├────────────────────────┴─────────────────┤
│          选项（长度可变）    │   填充     │
└─────────────────────────────┴───────────┘
```

### 各字段详解

| 字段 | 大小 | 说明 |
|------|:--:|------|
| 源端口/目的端口 | 各2B | 运输层与应用层的接口 |
| **序号** | 4B | 本报文段数据**第一个字节**的序号 |
| **确认号** | 4B | 期望收到对方**下一个**报文段第一个字节的序号。确认号=N 表示 N-1 及之前都已正确收到 |
| 数据偏移 | 4位 | 首部长度(单位4B)，表示数据从哪开始 |
| **URG** | 1位 | 紧急指针有效，尽快传送 |
| **ACK** | 1位 | 确认号有效（ACK=0 时确认号无效）|
| PSH | 1位 | 推送，尽快交付应用进程 |
| RST | 1位 | 复位，释放连接重新建立 |
| **SYN** | 1位 | 同步序号，用于连接建立 |
| **FIN** | 1位 | 终止连接，数据发送完毕 |
| **窗口** | 2B | 允许对方发送的字节数（从确认号算起），**动态变化** |
| 检验和 | 2B | 伪首部+首部+数据（协议号=6）|
| 紧急指针 | 2B | URG=1 时指出紧急数据末尾位置 |
| 选项 | 可变 | MSS（最大报文段长度）、窗口扩大、时间戳等 |
| 填充 | 可变 | 使首部长度为 4B 的整数倍 |

### TCP 序号与确认号计算 ⭐

**序号**：本报文段数据部分第一个字节在整个字节流中的编号。

**确认号**：期望收到的下一个报文段的第一个数据字节的序号。

#### 例题（作业 5-23）

```
主机 A 向 B 连续发送两个 TCP 报文段，序号分别为 70 和 100。

(1) 第一个报文段携带了多少字节的数据？
   第一个报文段数据 = 序号70到99，共 30 字节

(2) B 收到第一个报文段后确认号是多少？
   期望收到的下一个字节序号 = 100，确认号 = 100

(3) 若 B 收到第二个报文段后确认号是 180，第二个报文段数据多少？
   第二个报文段数据 = 180 - 100 = 80 字节

(4) 若第一个报文段丢失，B 收到第二个报文段后确认号？
   期望收到的第一个缺失字节 = 70，确认号 = 70
```

## 5. 可靠传输的工作原理

### 5.1 停止等待协议

**工作方式**：每发送完一个分组就停止，等到确认后再发下一个。

**三种情况**：

1. **无差错**：A 发 M1 → B 收 M1 回 ACK → A 收到 ACK 发 M2

2. **出现差错**（B 收到错误或 M1 丢失）：
   - B 不做任何事
   - A 超时重传（超时计时器到期未收到确认）
   - 需要暂存已发送分组的副本

3. **确认丢失/迟到**：
   - ACK 丢失：A 超时重传，B 收到重复分组 → 丢弃 → 重发 ACK
   - ACK 迟到：A 超时重传，收到重复 ACK → 丢弃

**停止等待协议要点**：
- 编号：对分组和确认都编号（否则无法区分新旧）
- 超时重传：比平均 RTT 长一些
- 暂存副本
- 优点：简单；缺点：**信道利用率太低**

### 5.2 连续 ARQ 协议（流水线传输）

**改进**：不等确认，连续发送多个分组。

- **发送窗口**：窗口内的分组可连续发送
- **窗口滑动**：每收到确认，窗口向前滑动
- **累积确认**：确认号 N = N-1 及之前的数据都正确收到
- **Go-back-N**：出错时退回重传 N 个分组

## 6. TCP 可靠传输的实现

### 6.1 以字节为单位的滑动窗口

**发送方**：
```
P1 = 后沿（已发送并确认的边界）
P2 = 当前位置（已发送未确认/未发送的边界）
P3 = 前沿（允许发送的最大边界）

发送窗口 = P3 - P1
已发送未确认 = P2 - P1
可用窗口 = P3 - P2
```

**接收方**：只接收落入接收窗口内的数据。

**窗口滑动**：
- A 收到确认 → 发送窗口前移 → 可发送新数据
- 可用窗口 = 0 → 发送方暂时不能发送新数据
- A 超时 → 重传未确认数据

### 6.2 超时重传时间的选择

**加权平均往返时间 RTTS：**

$$新的 RTTS = (1-\alpha) \times 旧的 RTTS + \alpha \times 新的 RTT 样本$$

**超时重传时间 RTO：**

$$RTO = RTTS + 4 \times RTTD$$

$$新的 RTTD = (1-\beta) \times 旧的 RTTD + \beta \times |RTTS - 新的 RTT 样本|$$

其中 β 推荐值 = 1/4。

### 6.3 Karn 算法

**问题**：重传后收到确认，无法区分是对原报文还是重传报文的确认。

**Karn 算法**：
- **重传的报文段，其 RTT 样本不计入 RTTS**
- **每重传一次，RTO = γ × 旧 RTO**（γ=2）
- 只有不再重传时，才重新计算 RTT

### 6.4 选择确认 SACK

只重传缺失的字节块，不重传已正确到达的数据。

## 7. TCP 流量控制

### 7.1 利用滑动窗口实现流量控制

**流量控制**：让发送方发送速率不要太快，使接收方来得及接收。

- 接收方通过**窗口字段**通知自己的接收窗口 (rwnd)
- 发送方的发送窗口不能超过接收方给出的窗口值
- rwnd = 0 → 发送方暂停发送

### 7.2 死锁与持续计时器

**死锁场景**：
1. B 发送 rwnd=0 → A 停止发送
2. B 缓存有空余 → 发送新的 rwnd≠0 → **这个报文丢失**
3. A 等 B 通知，B 等 A 发数据 → 死锁！

**解决**：**持续计时器**
1. A 收到零窗口 → 启动持续计时器
2. 到期 → 发送**零窗口探测报文段**（携带1字节数据）
3. B 回复当前窗口值
4. 窗口仍为0 → 重新设置持续计时器
5. 窗口不为0 → 死锁打破

### 7.3 糊涂窗口综合症

**现象**：每次只发送/接收极少字节，有效数据传输率极低。

**发送方糊涂窗口**：应用进程每次只写入1字节，TCP立刻发送。
→ 解决：Nagle 算法（积累到 MSS 或收到 ACK 再发）

**接收方糊涂窗口**：应用进程每次只读取1字节，窗口只增加1字节。
→ 解决：接收方等待缓存有足够空间（MSS 或一半缓存）再发确认

## 8. TCP 拥塞控制 ⭐⭐⭐（必考）

### 8.1 拥塞控制原理

**拥塞**：对网络中某资源的需求超过了该资源可用部分，网络性能下降。

**拥塞控制 vs 流量控制**：

| | 拥塞控制 | 流量控制 |
|--|--------|--------|
| 控制对象 | 全网负载 | 点对点 |
| 目的 | 防止网络过载 | 防止接收方来不及收 |
| 范围 | 全局 | 一条TCP连接 |
| 发送方 | 控制注入网络的速率 | 匹配接收方能力 |

**发送窗口上限 = Min(rwnd, cwnd)**

### 8.2 四种拥塞控制算法

#### (1) 慢开始 (Slow Start)

- 初始 cwnd = 1（报文段）
- 每收到一个**对新报文段的确认** → cwnd + 1
- 效果：**每经过一个 RTT（传输轮次），cwnd 翻倍**（指数增长）
- "慢开始"并不慢——指数增长很快！

#### (2) 拥塞避免 (Congestion Avoidance)

- 当 cwnd ≥ ssthresh（慢开始门限）时启用
- 每经过一个 RTT → cwnd + 1（**加法增大 AI**）
- 效果：**线性增长**
- 目的：让窗口缓慢增长，避免拥塞

#### (3) 快重传 (Fast Retransmit)

- 接收方每收到一个失序报文段 → 立即发送**重复确认**
- 发送方连续收到**3 个重复确认** → 立即重传丢失报文段（不等超时）
- 可使整个网络吞吐量提高约 20%

#### (4) 快恢复 (Fast Recovery)

- 收到 3 个重复确认后（不执行慢开始）：
  1. ssthresh = cwnd / 2（**乘法减小 MD**）
  2. cwnd = ssthresh
  3. 执行拥塞避免算法（**加法增大 AI**）

### 8.3 网络拥塞时的处理

发生超时（判断网络拥塞）：
- ssthresh = max(cwnd / 2, 2)
- **cwnd = 1**
- **重新慢开始**

### 8.4 完整拥塞控制流程图

```
连接建立
  ↓
cwnd = 1, ssthresh = 初始值
  ↓
┌─→ cwnd < ssthresh → 慢开始（指数增长）
│     ↓
│   cwnd ≥ ssthresh → 拥塞避免（线性增长）
│     ↓
│   收到3个重复ACK → 快重传+快恢复
│     │                  ssthresh=cwnd/2
│     │                  cwnd=ssthresh
│     │                  进入拥塞避免
│     ↓
│   超时 → 网络拥塞
│     │    ssthresh=cwnd/2
│     │    cwnd=1
│     └──→ 重新慢开始（返回上面循环）
└─── 循环
```

### 8.5 拥塞控制综合例题（作业 5-39）⭐

### 8.6 主动队列管理 AQM

- **RED（随机早期检测）**：
  - LAV < THmin → 不丢弃
  - THmin ≤ LAV ≤ THmax → 以概率 p 丢弃
  - LAV > THmax → 全部丢弃

- 避免"全局同步"问题（多个TCP连接同时进入慢开始）

## 9. TCP 运输连接管理 ⭐⭐

### 9.1 三报文握手建立连接

```
客户端 A                                 服务器 B
CLOSED                                  CLOSED
  │（B 先创建 TCB，LISTEN）
  │                                        │
  ├── SYN=1, seq=x ──────────────────────→│ SYN-SENT
  │                                        │
  │←── SYN=1, ACK=1, seq=y, ack=x+1 ─────┤ SYN-RCVD
  │                                        │
  ├── ACK=1, seq=x+1, ack=y+1 ──────────→│
  │                                        │
ESTABLISHED                            ESTABLISHED
```

**关键要点**：
- SYN 报文段**不携带数据**，但消耗一个序号
- 第二个报文 SYN=1, ACK=1
- 第三个 ACK 报文可携带数据，不携带数据时不消耗序号
- **三报文握手防止已失效的连接请求导致连接错误**

### 9.2 四报文挥手释放连接

```
客户端 A                                 服务器 B
ESTABLISHED                            ESTABLISHED
  │                                        │
  ├── FIN=1, seq=u ─────────────────────→│
FIN-WAIT-1                                │
  │←── ACK=1, seq=v, ack=u+1 ───────────┤ CLOSE-WAIT
FIN-WAIT-2                                │（半关闭：A不再发，B仍可发）
  │                                        │
  │←── FIN=1, ACK=1, seq=w, ack=u+1 ────┤ LAST-ACK
  │                                        │
  ├── ACK=1, seq=u+1, ack=w+1 ──────────→│
TIME-WAIT                               CLOSED
  │（等待 2MSL）                           │
CLOSED
```

**关键要点**：
- FIN 报文即使不携带数据也消耗一个序号
- 半关闭状态：A→B 方向关闭，B→A 方向仍可发送数据

### 9.3 为什么 TIME-WAIT 要等 2MSL？

1. **保证最后一个 ACK 能到达 B**：B 超时会重传 FIN，A 可再次确认
2. **防止"已失效的连接请求报文段"出现在新连接中**

### 9.4 保活计时器

- 默认 **2 小时**
- 超时 → 发探测报文段
- 连续 10 个探测（间隔 75 秒）无响应 → 终止连接

### 5-37：四种拥塞控制算法的区别
慢开始=指数增长，拥塞避免=线性增长，快重传=3个重复ACK立即重传，快恢复=收到3个重复ACK后cwnd减半+线性增长。乘法减小→超时时ssthresh减半。加法增大→拥塞避免阶段线性加1。

### 5-74：流量控制 vs 拥塞控制
流量控制=接收方限制发送方；拥塞控制=防止网络过载。发送窗口上限 = min(rwnd, cwnd)。rwnd<cwnd→取决于流量控制；cwnd<rwnd→取决于拥塞控制。

### 5-39：拥塞窗口-RTT 综合题
见 8.5 节。这是最重要的综合题，涵盖了所有拥塞控制的知识点。
